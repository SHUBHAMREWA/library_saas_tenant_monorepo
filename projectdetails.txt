# Library Management SaaS — Initial Product & Architecture Brief

You are acting as a **Senior System Architect, Product Engineer, UI/UX Engineer, Backend Engineer, Database Architect, Security Engineer, and QA Engineer**.

We are going to build a production-grade, scalable, mobile-first **Library Management SaaS platform**.

IMPORTANT:

At this stage, **DO NOT start implementing the application**.

First understand the complete product requirements below and create a detailed implementation plan and architecture proposal.

I will manually review your activity and plans before allowing you to implement major features.

---

# 1. PRODUCT VISION

The product is a SaaS platform for managing physical libraries, especially private study libraries / reading rooms / institute libraries.

The application should be:

* Extremely simple to use
* Mobile-first
* PWA
* Fast
* Professional
* Modern
* Scalable
* Secure
* Easy for non-technical library owners
* Designed so that RFID and networking/device integrations can be added in the future

The UI should NOT feel AI-generated, generic, or like a basic CRUD dashboard.

It should feel like a real commercial SaaS product.

Prioritize:

* Clear information hierarchy
* Excellent mobile UX
* Large touch targets
* Simple workflows
* Good empty states
* Good loading states
* Good error states
* Consistent typography
* Consistent spacing
* Professional forms
* Useful dashboards
* Minimal unnecessary animations

---

# 2. SAAS MODEL

This is a MULTI-TENANT SaaS application.

There will be two major platform-level concepts:

## Main Platform Admin

The platform owner/admin manages the entire SaaS.

Admin can:

* View users
* View libraries
* View subscriptions
* Manage subscription plans
* Manually activate subscriptions
* Suspend libraries
* Manage payments
* Manage coupons
* Create/edit/disable coupons
* View audit logs
* Manage platform-level settings

## Library Owner / User

A normal user can:

* Create an account
* Create multiple libraries
* Manage each library
* Create rooms
* Create rows
* Create seats
* Add students
* Assign students to seats
* Manage memberships
* Manage attendance
* View dashboard
* Manage library settings
* Manage subscription

One user can own MULTIPLE libraries.

Do NOT design the database assuming:

user = one library.

The architecture must support:

User → many Libraries.

---

# 3. MULTI-TENANCY

This is one of the most important requirements.

Use a proper multi-tenant architecture.

Core relationship:

User
↓
Library
↓
Library Members / Staff
↓
Library Resources

A user may have access to multiple libraries.

Future roles should be possible:

* OWNER
* ADMIN
* MANAGER
* STAFF

Every library-owned resource must be protected by tenant authorization.

A user belonging to Library A must NEVER be able to access Library B's:

* students
* rooms
* rows
* seats
* attendance
* payments
* memberships
* documents
* notifications
* reports

Do not rely only on frontend checks.

Authorization MUST happen on the backend.

---

# 4. LIBRARY STRUCTURE

The physical library structure is:

Library
↓
Room
↓
Row
↓
Seat

Example:

Library:
Knowledge Hub

Room:
Ground Floor

Rows:

Row A

* Seat A-01
* Seat A-02
* Seat A-03

Row B

* Seat B-01
* Seat B-02
* Seat B-03

The owner should be able to:

* Create room
* Rename room
* Archive room
* Create rows
* Rename rows
* Archive rows
* Generate seats
* Rename seats
* Change seat status
* Reorder seats where appropriate

Seats should support sequence/order.

The data model should NOT treat seats as simple text values.

Seats need stable IDs so future RFID/device integration can associate hardware with a physical seat.

---

# 5. STUDENT MANAGEMENT

Library owners can add students.

Student information:

* Name
* Phone number
* Email
* Address
* Father's name
* Mother's name
* Purpose for study
* Profile photo
* Aadhaar document/photo

Student functionality:

* Add student
* Edit student
* View student
* Search student
* Filter student
* Archive student
* View complete student history

Student documents/images should be stored using Cloudinary.

Do not store large binary files directly in PostgreSQL.

Store appropriate metadata/reference information in PostgreSQL.

Aadhaar documents are sensitive.

Design the system so that they are access-controlled and are not unnecessarily exposed publicly.

---

# 6. STUDENT MEMBERSHIP

A student can join the library for a period.

Example:

Student joins:

4 February

Expected end:

4 March

But the owner does NOT necessarily know whether the student will continue.

Therefore the system needs membership lifecycle management.

Membership states should support concepts such as:

* UPCOMING
* ACTIVE
* PAUSED
* EXPIRED
* CANCELLED

The system should calculate:

* Active students
* Upcoming memberships
* Memberships ending today
* Memberships ending within 5 days
* Memberships ending within 7 days
* Expired memberships
* Paused memberships

The dashboard should prominently show memberships requiring attention.

---

# 7. MEMBERSHIP HISTORY

Student history is extremely important.

Do not overwrite historical information.

We should be able to understand:

* When student joined
* When membership ended
* When membership was renewed
* When membership was paused
* Why it was paused
* When membership resumed
* Which seat was assigned
* When the student changed seats
* Attendance history

Historical records should remain auditable.

---

# 8. MEMBERSHIP PAUSE / GAP

Sometimes a student cannot attend for several days.

Example:

Membership:

4 Feb → 4 Mar

Pause:

15 Feb → 20 Feb

Reason:

College examination

The system should record this as a separate membership pause/history record.

Do NOT simply overwrite the original membership data.

The architecture should support configurable future business rules regarding whether pause days extend membership duration.

---

# 9. SEAT ASSIGNMENT

A student should NOT permanently belong to one seat.

Instead use a historical seat-assignment model.

Example:

February:

Student Rahul → A-12

March:

Student Rahul → A-15

April:

Student Rahul → B-03

Therefore seat assignments should contain concepts such as:

* student
* seat
* start date
* end date
* status

The system should prevent conflicting active assignments.

---

# 10. ATTENDANCE

Initially attendance should be manual.

But the architecture MUST support future attendance sources.

Possible sources:

* MANUAL
* QR
* RFID
* DEVICE
* OTHER FUTURE PROVIDERS

Create an abstraction such as an Attendance Provider / Attendance Service.

Do not hard-code the entire application around manual attendance.

Future architecture:

RFID Reader
↓
Device Gateway
↓
Attendance Service
↓
Application
↓
Database

The initial version only needs:

Manual check-in
Manual check-out
Attendance history
Student attendance history
Daily attendance

---

We are NOT implementing RFID right now.

However, the architecture must allow it later.

Future devices may include:

* RFID readers
* Attendance devices
* Seat sensors
* Door controllers
* Printers
* Other networking devices

Potential future architecture:

Physical Device
↓
Device Gateway
↓
WebSocket / MQTT
↓

↓
Redis
↓
PostgreSQL

Do NOT introduce unnecessary IoT infrastructure into V1.

Just design clean interfaces so it can be added later.

# 12. OWNER DASHBOARD

The owner dashboard should answer:

"What's happening in my library right now?"

Important metrics:

* Total active students
* Today's attendance
* Available seats
* Occupied seats
* Memberships ending soon
* Expired memberships
* Upcoming memberships
* Recent activity

Example:

128 Active Students

14 Memberships Ending Soon

92 Students Present Today

25 Available Seats

The dashboard should prioritize actionable information instead of decorative analytics.

Mobile layout is the priority.

---

# 13. SUBSCRIPTION

A library cannot operate normally unless its subscription is active.

The SaaS will have subscription plans.

Potential plans:

* FREE/TRIAL
* BASIC
* PRO
* ENTERPRISE

The architecture must support changing plans later.

Do NOT implement:

library.isPaid = true

Instead use a proper subscription model.

Subscription should contain concepts such as:

* library
* plan
* status
* start date
* end date
* provider
* provider subscription ID
* auto-renew
* created/updated timestamps

Subscription statuses should support:

* TRIAL
* ACTIVE
* PAST_DUE
* EXPIRED
* CANCELLED
* MANUAL

---

# 14. MANUAL ADMIN SUBSCRIPTION

Platform admin must be able to manually give subscription access.

Example:

Admin gives:

PRO plan

Valid:

1 September → 1 December

This should be represented as a normal subscription record with an appropriate provider/source such as:

ADMIN / MANUAL

Do not bypass the normal subscription system.

The rest of the application should simply ask:

"Does this library currently have an active subscription?"

---

# 15. PAYMENTS

Payment gateways:

* Razorpay
* Cashfree

Create a payment abstraction.

Conceptually:

PaymentService
↓
PaymentProvider
├── RazorpayProvider
└── CashfreeProvider

The application should not tightly couple business logic to a single payment provider.

Payment records should contain appropriate:

* library
* subscription
* provider
* provider payment ID
* provider order/subscription ID
* amount
* currency
* status
* timestamps

Payment webhooks MUST be idempotent.

If the same webhook is received multiple times, it must NOT create duplicate payments or duplicate subscriptions.

---

# 16. COUPONS

Platform admin can create coupon codes.

Example:

LIBRARY20

20% discount.

Coupon system should support:

* percentage discount
* fixed discount
* minimum amount
* maximum discount
* start date
* expiry date
* usage limit
* per-user usage limit
* active/inactive status

Coupon calculation must happen on the backend.

Never trust discount values calculated by the frontend.

---

# 17. AUTHENTICATION

Support:

* Google Sign In
* Email OTP login

Authentication should be secure.

Consider:

* OTP expiration
* OTP rate limiting
* brute-force protection
* session security
* account linking
* logout
* protected APIs

Authentication and authorization are different concerns.

---

# 18. FILE STORAGE

Use Cloudinary.

Images should be optimized.

Requirements:

* compression
* WebP conversion
* responsive image transformations
* CDN delivery

Prefer direct/signed uploads rather than sending unnecessarily large files through the Node.js API.

PostgreSQL should store metadata/reference information rather than large binary files.

---

# 19. PWA

The application MUST be a Progressive Web App.

Target users will primarily use mobile phones.

Implement eventually:

* Web App Manifest
* Service Worker
* Installability
* Offline app shell
* Appropriate caching
* Push notifications

Do NOT blindly cache sensitive information.

Student documents must not be exposed through unsafe caching.

---

# 20. NOTIFICATIONS

The system should eventually send notifications for important events.

Examples:

* Membership ending in 5 days
* Membership ending tomorrow
* Membership expired
* Payment successful
* Payment failed
* Subscription expiring

Architecture should support:

Business Event
↓
Notification Service
↓
Queue
↓
Worker
↓
Push Notification

Use Redis + background workers where appropriate.

Avoid doing heavy background work inside API requests.

---

# 21. KANBAN

A simple Kanban feature may be included.

It should NOT become a complicated project-management system.

Basic functionality:

* Columns
* Cards
* Drag and drop
* Reorder
* Persist position

No unnecessary animations.

It must work properly with touch interaction on mobile.

Keep the Kanban component reusable.

---

# 22. UI / UX

The application must be MOBILE FIRST.

Do not design desktop first and then shrink it.

Design mobile screens first.

Important mobile requirements:

* Large touch targets
* Simple navigation
* Bottom navigation where appropriate
* Easy forms
* Step-based student creation
* Responsive tables/cards
* Avoid horizontal scrolling
* Proper keyboard handling
* Loading states
* Skeleton states
* Empty states
* Error states
* Confirmation dialogs for destructive actions

Desktop should then adapt from the mobile-first design.

The interface should look like a polished SaaS product.

Avoid:

* excessive gradients
* unnecessary animations
* huge dashboards
* excessive shadows
* inconsistent cards
* random colors
* AI-looking generic UI
* overly complicated navigation

# 27. DATABASE PRINCIPLES

Use PostgreSQL.

Use:

* UUIDs
* foreign keys
* indexes
* unique constraints
* timestamps
* transactions
* soft deletion where appropriate

Important:

Design indexes based on actual query patterns.

Prevent N+1 queries.

Do not expose database models directly as API responses.

Use DTOs / schemas where appropriate.

---

# 28. SECURITY

Security must be considered from the beginning.

Protect against:

* unauthorized tenant access
* IDOR
* privilege escalation
* SQL injection
* XSS
* CSRF where relevant
* brute force
* OTP abuse
* malicious uploads
* payment webhook spoofing
* sensitive document exposure
* insecure admin access

Sensitive operations should be auditable.

---

# 29. AUDIT LOGGING

Important mutations should create audit records.

Examples:

* Student created
* Student archived
* Seat assigned
* Seat changed
* Membership extended
* Membership paused
* Subscription manually activated
* Coupon created
* Coupon disabled
* Admin action

Audit logs should contain enough information to understand:

WHO
did WHAT
to WHICH RESOURCE
WHEN
